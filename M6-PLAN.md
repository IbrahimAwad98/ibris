# M6 plan — text editing

Written before any M6 code, as required. This is the hardest feature in
the project; the plan's job is to say what is achievable, what is not,
and where the boundaries are hard. The conclusion up front: **M6 must be
split across sessions**, and the first slice is deliberately narrow.

---

## 1. What PDFium actually offers

The public surface relevant to editing text that already exists:

| API | What it gives |
| --- | --- |
| `FPDFPage_CountObjects` / `GetObject` / `FPDFPageObj_GetType` | Enumerate page objects; text objects are type 1 |
| `FPDFTextObj_GetText` | The object's text, via the page's textpage |
| `FPDFText_SetText` | Replace a text object's entire string (UTF-16 in) |
| `FPDFTextObj_GetFont` + `FPDFFont_*` | Font handle: name, flags, glyph paths |
| `FPDFPageObj_GetMatrix` / bounds | Placement; untouched by SetText |
| `FPDFPage_GenerateContent` | Rewrite the content stream after edits |

What PDFium does **not** offer, and no amount of cleverness changes:

- **No glyph additions.** `FPDFText_SetText` re-encodes against the
  font as embedded. If the font is a subset without the replacement's
  glyphs, PDFium writes charcodes that render as blanks/tofu — it does
  not extend the subset. Extending a subset means parsing and rewriting
  the font program (glyf/loca/cmap or CFF charstrings) ourselves.
- **No reflow.** A text object is positioned by its matrix; PDF has no
  paragraph model. Making a longer line push the next line down means
  re-typesetting neighbouring objects ourselves — heuristically, since
  "the next line" is just another positioned object.
- **No partial-object editing below the string level.** Kerning arrays
  (TJ offsets) inside the object are regenerated by PDFium; hand-tuned
  spacing in the original may shift subtly after any edit.

## 2. The slice that ships first (M6a)

**Editing an existing text run, in place, where the replacement uses
only glyphs the embedded font already has.**

User flow: a "Edit text" tool; clicking a text run shows an inline
editor primed with the object's current text; on confirm, an undoable
`edit-text` command records `{pageIndex, objectIndex, before, after}`.
At save, the engine (fresh raw load, decision 013 pipeline) locates the
object, calls `FPDFText_SetText`, `FPDFPage_GenerateContent`, and the
usual rewrite. The viewing document is edited the same way in memory so
the bitmap refreshes (or the save takes the rebase path — decided at
implementation by which is less invasive).

**Glyph gate:** before accepting an edit, every char of the replacement
is checked against the object's font (`FPDFFont_GetGlyphPath` returning
a non-empty path, ASCII fast-path for the 14 standard fonts). If any
glyph is missing, the edit is **refused with a clear message** ("this
font's embedded subset does not contain 'ñ'") — never accepted and
rendered as tofu.

**Hard boundaries of M6a, stated in the UI where relevant:**

- No reflow: the run's box may grow or shrink; neighbours do not move.
- One object at a time: a visual "paragraph" spanning objects edits per
  object; runs split mid-word by the generator edit awkwardly. Shown as
  is — honesty over illusion.
- Text inside Form XObjects: not editable (not enumerated at page level).
- Rotated/skewed text: editable (matrix untouched), the editor overlay
  just won't be WYSIWYG for extreme transforms.
- Type3 fonts, vertical writing: refused.

**Corruption safety, the non-negotiable:** every save that includes an
`edit-text` command re-extracts the page text afterwards *before the
atomic rename* and verifies the replacement is present and the rest of
the page's text is unchanged. Any mismatch aborts the save, leaving the
on-disk file untouched (the temp+rename pipeline already guarantees
this). A narrow feature that always works beats a broad one that
sometimes destroys files.

## 3. Later slices (explicitly not M6a)

- **M6b — subset extension:** embed missing glyphs by rewriting the
  font program. TrueType first (glyf/loca/cmap are tractable); CFF
  later or never. This is a font-tooling project of its own; evaluate
  a permissive-licensed crate (e.g. `ttf-parser` family, MIT/Apache)
  before hand-rolling.
- **M6c — same-line reflow:** shift the remainder of the line when a
  run's advance width changes; requires reliable line grouping from
  char geometry (the search/selection code already approximates it).
- **M6d — paragraph reflow:** re-typesetting neighbouring objects.
  Honestly may never ship; every PDF editor that does it produces
  documents that no longer match their source. Decide when M6c exists.

## 4. Session split

M6a alone is a full session's work (tool UI + command + engine +
glyph gate + verification pass + fixtures with subset fonts). M6b is at
least another. Nothing in M6a's design forecloses M6b/c — the command
shape (`before`/`after` per object) is the same regardless of how
capable the writer becomes.
